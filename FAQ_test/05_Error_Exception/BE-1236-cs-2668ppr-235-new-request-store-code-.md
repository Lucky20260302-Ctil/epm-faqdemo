# BE-1236: [CS-2668/PPR-235] New Request - Store code logic enhance for C360 API call

## 問題描述

Target module in scope should be **C360CRMInterface**.
Therefore, the affected regions are: **Coach Japan, Coach ANZ, and Kate Spade ANZ**.

2. **Enhancement Location**

The proposed enhancement will be implemented in **C360CRMInterface**, specifically within the SQL script responsible for selecting **StoreNum **only , replacing the original derivation logic.

3. **Understanding the Original Logic**

After a detailed review, we believe the legacy logic `LEFT(vip_no, 4)` was originally intended to represent the **VIP issuing store location**.
This aligns with the VIP number format generated by **Ename, Ename Tourist, and FEPOS**, which follows:
`[ShopLoc][Till][Prefix][Running Sequence]`.

4. **Proposed StoreNum Logic for C360**

When passing StoreNum to C360 via RESTful calls, we propose the following priority to best reflect the intended business purpose:

1. **crmreg_loc**

2. **vip_issue_loc**

3. **vip_firstpurchase_loc** (new virtual field)

5. **About vip_firstpurchase_loc**

- This is a **new virtual field** derived from locating the **earliest normal sales transaction** associated with the VIP number.

- The **shoploc** of that earliest transaction will be used.

- This value may differ from the VIP issuing location, and in some cases it may be empty.

1. **Additional query for first transaction**

To derive the first transaction for a VIP, an additional query on transaction history is required. This will inevitably introduce extra DB enquiry cost, especially for VIPs with a long transaction history or under high‑volume scenarios. We should therefore treat this as a measurable performance impact rather than a “free” lookup.

2. **Caching consideration**

Caching does not appear to be suitable in this case. The payload is queried and sent to C360 in real time, and the relationship between VIP × first transaction location is not frequently reused across requests. Maintaining and invalidating such a cache would introduce overhead that outweighs the potential benefit, making it **not cost‑effective** for the current use case.

3. **Indexing as a mitigation option**

From a DB optimization perspective, adding or refining indexing on the join/view (e.g. relationship between **vipno**, **transaction date**, and **location**) would be the most practical approach to mitigate performance impact. This is something we can further evaluate based on actual execution plans and volume assumptions.
